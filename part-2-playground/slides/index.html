Model and harness

A model is the brain. It reads text and writes text.

A harness is the hands for the brain: the program around the model, with the tools, the loop, the permissions and the context.

An agent is the two working together.

Claude is a model. Claude Code is a harness.

  you
   │  prompt
   ▼
┌─ harness: Claude Code ──────────────┐
│  tools  permissions  context  files │
└───────┬──────────────────▲──────────┘
        │ request          │ answer or tool call
        ▼                  │
┌─ model: Claude ──────────┴──────────┐
│  predicts the next text             │
└─────────────────────────────────────┘

The harness runs the tool call, adds the
result and asks the model again.

Words we use today

You see these words in the interface of Claude Code.

The context grows with each turn. Each prompt, answer and tool result stays in the window and goes out again with the next request.

The bigger the context, the higher the cost of each request.

token           a small piece of text;
                the unit of size and cost

context window  all the text the model sees
                in one request

tool            an action the harness runs:
                read a file, run a command

permission      what runs without asking you

CLAUDE.md       project notes, loaded
                in each session

MCP             a way to connect outside
                systems as new tools

The playground

A small company on your own computer.

  • Traefik, the HTTP load balancer, sits in front of all web traffic.
  • GitLab keeps the code and starts the pipelines.
  • GitLab Runner runs each job in Docker-in-Docker.
  • test and prod are the two servers.

Each name is a container in one Docker Compose project. Traefik carries only the web traffic: git and the deploys connect to their containers directly, over SSH.

┌─ your computer ─────────────────────────┐
│  browser, Claude Code, git, ssh         │
└───┬─────────────────────────────────────┘
    │ HTTPS
┌───▼─ Docker Compose ────────────────────┐
│  Traefik: HTTP load balancer            │
│    │          │         │               │
│    ▼          ▼         ▼               │
│  GitLab      test      prod             │
│    │          ▲         ▲               │
│    ▼          │ deploy  │ over SSH      │
│  GitLab Runner ─────────┘               │
│    │ runs the jobs in                   │
│    ▼                                    │
│  Docker-in-Docker                       │
└─────────────────────────────────────────┘

What we build

A small web app that tells you who called it: the host name, the IP addresses and the request headers.

Its pipeline grows with the app:

  • Iteration 1: unit tests, build, integration test.
  • Iteration 3: deploy to test on a merge, and to prod when a person says so.

We use Go. Any language works if you install it on the servers.

push
  │
  ▼
test          unit tests
  ▼
build         the binary, kept as an artifact
  ▼
integration   start the binary, call it with curl
  ▼
deploy-test   automatic after a merge to main
  ▼
deploy-prod   manual: a person starts it

Permission modes

    
A mode decides how much Claude does without asking you.

    
In auto mode, a second model checks the actions and blocks what looks dangerous or leaves your environment.

    
Allow and deny rules come first.

    
ShiftTab changes the mode.

  

  


Manual   asks you before actions

Accept   edits files with no question,
edits    asks before commands

Plan     reads and plans,
         changes no source file

Auto     no routine questions;
         a classifier checks the actions

  






  

    
Plan before code

    
In plan mode Claude reads and plans. It changes nothing until you approve.

    
The plan is yours: tell Claude what to change, then approve.

    
A good prompt has four parts: the task, the context, the limits and the check.

    
CtrlG opens the plan in your editor.

  

  

    

    
When the plan is ready but you are not happy with it, tell Claude what to change
