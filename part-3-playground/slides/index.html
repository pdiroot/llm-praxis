What we do today

  • We let Claude Code work longer without us.
  • We give it subagents, each with its own job.
  • We write our process down once and run it with one command.

Each step hands more of the work to Claude Code. You stay in charge of what "done" means.

We cover

  • Loops: `/loop`, `/goal` and routines
  • Subagents: an implementer and a reviewer
  • A skill: `/make-it-so`
  • Plugins and marketplaces: `skill-creator`
  • A workflow: research in four stages

In later sessions

  • Workspace mode with many repositories
  • Spec-driven development
  • The same tasks in other AI harnesses
  • Running local LLMs

Four kinds of loop

    
Each kind hands more to Claude Code. In a turn, Claude decides when it is done. With /goal, a separate model, the evaluator, decides. With /loop, a timer starts the prompt again. A routine runs in the cloud, with no laptop.

  

  


turn       you prompt, Claude works, and Claude stops
           when it thinks it is done

/goal      the evaluator, a small model, checks your
           condition after each turn. Claude goes on
           until it is true

/loop      the same prompt again every few minutes,
           in this session

routine    a prompt on a schedule or an event, in the
           cloud, with the laptop closed

Routines: loops in the cloud

    
A /loop lives in this session. When the laptop sleeps, it stops.

    
A routine runs in the cloud: on a schedule, from an API call or on a GitHub event. You set the prompt, the repository and the connectors one time.

    
The routine runs on Anthropic's cloud, so Anthropic must have access to the repository, through GitHub.

    
It fits a GitHub project that you can share with Anthropic, such as an open-source project. For company code, ask your security team first.

    
To create a routine, type /schedule in Claude Code and describe the task. Claude sets up the routine for you.

  

  


/schedule every weekday at 8:00, summarize the new
issues and open a PR for the easy ones

/schedule when a PR fails CI, find the cause and
push a fix

What a subagent is

    
A subagent has its own context window, its own model and its own tools. It does one job and gives back a summary.

    
The context window of your main session stays small. The files that the subagent reads stay in the window of the subagent.

    
Do not start a subagent for one simple question. Each subagent first loads its own system prompt, tools and CLAUDE.md: thousands of tokens before it does any work. Give it a job that is worth that cost.

    
A subagent can start subagents too, up to three levels deep.

  

  


---
name: reviewer
description: Reviews a Python change for bugs,
  security, edge cases and design.
model: opus
effort: high
tools: Read, Glob, Grep, Bash
---

You are a Python code reviewer. You never edit.
Give each finding a severity, the file
and the line.

    
No Edit and no Write tool. Bash stays, for `git diff` and the tests.

  






  

    
A model and an effort for each job

    
Writing code and running checks is simple work. A fast model does it well.

    
Judging a design needs the strongest model and time to think.

    
/effort sets how long Claude thinks: low, medium, high, xhigh, max.

  

  


implementer   Sonnet: writes the code and the tests,
              runs ruff and the tests

reviewer      Opus, high effort: reads only, judges
              the design and the security

    

    
A rule that must apply each time belongs in a hook, not in a prompt.

    
A hook can run ruff after each edit, whatever the model decides.

The advisor

    
A model at least as strong as the main one. Claude calls it on its own at key moments: before the real work, when it is stuck, and before it says "done".

    
Each call reads the whole conversation again, with no cache, so the advisor increases the cost.

    
An example: a session that costs $100 can cost $250 with the advisor.

    
The advice comes back encrypted: only the main model can read it, so you cannot judge it.

    
I do not recommend it. The reviewer subagent does the same job, and you control it: its model, its effort and its prompt.

Build until done

    
Now Claude is the loop. /goal takes a condition and starts work at once.

    
After each turn, the evaluator reads the conversation and checks the condition. The evaluator is a small, fast model. It is not the reviewer and not the advisor. While the condition is false, Claude goes on: build, review, fix, review again.

    
Write a condition that Claude can prove from the transcript: a test run, a review verdict.

    
Add a turn limit to the condition, such as "Stop after 10 turns", to keep the run short.

    
Tip: add "Wait for the report of the subagent". If not, Claude can end a turn while the subagent still works, and the goal has nothing to check.

What a skill is

    
A folder with a SKILL.md: a description and the steps. Scripts and notes can sit next to it.

    
Claude reads only the description until the skill is needed. Then it reads the rest.

    
You start it with /name. Claude can also start it when the description matches the task, unless the skill turns that off.

  

  


---
name: make-it-so
description: Takes a feature request from
  idea to a merge request: interview,
  implementer, reviewer, fixes,
  /simplify, checks, merge request.
argument-hint: <feature request>
---

1. Interview ...
2. Branch ...
3. Build: the implementer ...

Plugins and marketplaces

What skill-creator changed

    
It read the skill and the history of this session. Then it wrote down what went wrong in the session.

    
Evals go further: the same tasks run with and without the skill, and a grader compares the results.

  

  


- Checks joined with ";" let a commit pass while ruff
  failed. Use "&&".
- __pycache__ files got into a commit.
- Subagent reports can be empty or wrong: check each
  one yourself.
- Keep numbers in the notation at 4 digits at most.
- Remove a test only when it is a true duplicate.
- Read untrusted code before you run it: the eval in
  merge request !1.

What a workflow is

    
With subagents, Claude decides turn by turn what runs next.

    
With a workflow, Claude first writes a short script for this one task: which agents run, how many in parallel, who checks whose work. Then the script runs.

    
Claude writes its own harness for the task. To start one, write "use a workflow" in the prompt. The word "workflow" alone does not start one.

  

  


collect    4 agents, one for each tool, read the docs
   │
verify     4 agents open each source again and check
   │       each claim
table      the main session builds one table with a
   │       link in each cell
advise     the next three features

    
Claude chose this plan in the rehearsal. Your run can differ: you see the plan and approve it.

When to use a workflow, and its budget

    
A workflow uses many more tokens than one session. Give it a limit in the prompt: the number of agents or the tokens.

    
Use one when the work splits into many parts that each need a check: a migration, an audit, a research task, the triage of a thousand items.

    
Do not use one for a change you can see in one file.

  

  


/goal      when is it done
/loop      when does it run again
workflow   who does each part
