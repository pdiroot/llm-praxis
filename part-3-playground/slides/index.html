What loops are for

    
Anything you check again and again by hand.

    
When I am on call, my agents fetch the metrics every 20 minutes. When the metrics show that a server or an app can fail soon, they start an investigation. When the alert comes, the first findings are already there.

    
Give no interval, and Claude sets the pace itself. It checks often while something changes, less often when nothing does, and ends the loop when the job is done.

Routines: loops in the cloud

    
A /loop lives in this session. When the laptop sleeps, it stops.

    
A routine runs in the cloud: on a schedule, from an API call or on a GitHub event. You set the prompt, the repository and the connectors one time.

    
The routine runs on Anthropic's cloud, so Anthropic must have access to the repository, through GitHub.

    
It fits a GitHub project that you can share with Anthropic, such as an open-source project. For company code, ask your security team first.

    
To create a routine, type /schedule in Claude Code and describe the task. Claude sets up the routine for you.

What a subagent is

    
A subagent has its own context window, its own model and its own tools. It does one job and gives back a summary.

    
The context window of your main session stays small. The files that the subagent reads stay in the window of the subagent.

    
Do not start a subagent for one simple question. Each subagent first loads its own system prompt, tools and CLAUDE.md: thousands of tokens before it does any work. Give it a job that is worth that cost.

    
A subagent can start subagents too, up to three levels deep.

  

  


---
name: reviewer
description: Reviews a Python change for bugs,
  security, edge cases and design.
model: opus
effort: medium
tools: Read, Glob, Grep, Bash
---

You are a Python code reviewer. You never edit.
Give each finding a severity, the file
and the line.

    
No Edit and no Write tool. Bash stays, for `git diff` and the tests.

  






  

    
A model and an effort for each job

    
Writing code and running checks is simple work. A fast model does it well.

    
Judging a design needs the strongest model. For a small app like ours, medium effort is enough. Raise it for a large codebase.

    
/effort sets how long Claude thinks: low, medium, high, xhigh, max.

  

  


implementer   Sonnet: writes the code and the tests,
              runs ruff and the tests

reviewer      Opus, medium effort: reads only, judges
              the design and the security

    

    
A rule that must apply each time belongs in a hook, not in a prompt.

    
A hook can run ruff after each edit, whatever the model decides.

The advisor

    
A model at least as strong as the main one. Claude calls it on its own at key moments: before the real work, when it is stuck, and before it says "done".

    
Each call reads the whole conversation again, with no cache, so the advisor increases the cost.

    
An example: a session that costs $100 can cost $250 with the advisor.

    
The advice comes back encrypted: only the main model can read it, so you cannot judge it.

    
I do not recommend it. The reviewer subagent does the same job, and you control it: its model, its effort and its prompt.

Plugins and marketplaces

    
A plugin is a package of skills, subagents, hooks and MCP servers that you install as one unit.

    
A marketplace is a list of plugins, often a Git repository. The playground adds Anthropic's official marketplace for you.

    
A plugin runs code on your machine, with your rights: its hooks run shell commands on events, and its MCP servers run as programs. Read what it installs before you say yes.

    
The status line of iteration 1 is a plugin: one skill that copies one script. Writing your own is that small.

A hook: Ruff after each edit

    
Ruff is a linter and formatter for Python. CLAUDE.md asks Claude to run it before each commit. That is a request, and Claude can forget it.

    
A hook is a shell command that Claude Code runs on an event, such as after each edit. Claude does not decide to run it, so it runs each time.

    
Claude writes the hook as a small script. Exit code 2 sends what Ruff cannot fix back to Claude, and Claude fixes it.

    
The hook is in the project settings, so each session in the project gets it, also in a worktree.

  

  


"PostToolUse": [{
  "matcher": "Edit|Write|MultiEdit",
  "hooks": [{
    "type": "command",
    "command": ".claude/hooks/ruff-python.sh"
  }]
}]

What skill-creator can change

    
It makes the steps of a skill more exact. Your run can bring other improvements than ours, but they go the same way: clearer steps and fewer guesses.

    
Evals test a skill instead of trusting it. skill-creator writes a few test tasks and runs each one with and without the skill. A grader scores each result against a checklist.

    
So you see whether the skill helps at all, and whether your last change made it better or worse.

  

  

    
What it can change

    

      
descriptionWhen to use the skill, with example requests

      
briefsWhat each subagent must know: a subagent sees only its prompt

      
checksDo not take a subagent's word for it: run the tests and check git yourself

      
interviewFewer and better questions, with a recommended answer

      
rulesThe mistakes to avoid, such as a port that is in use

      
outputA fixed template for the merge request and the report

    

  






  

    
What the evals show

    
We compared the skill before and after skill-creator: three feature requests, each with the old and the new version.

    
Both versions built the features with tests, a review, /simplify and the checks. The new version also did what the old one left vague: a clear spec, a full merge request and a full report.

What a workflow is

    
With subagents, Claude decides turn by turn what runs next.

    
With a workflow, Claude first writes a short script for this one task: which agents run, how many in parallel, who checks whose work. Then the script runs.

    
Claude writes its own harness for the task. To start one, write "use a workflow" in the prompt. The word "workflow" alone does not start one.

verify

                    ↓
synthesize

  and recommends the next three features

Collect, verify, synthesize

    
A standard pattern for research. Sonnet agents do the many small reads, and Opus does the synthesis: a cheaper model for the volume, a stronger one for the judgment.

    
We do not name the tools. Claude picks the four most popular ones and says why.

    
You approve the script once. /workflows shows each agent while it works.

When to use a workflow, and its budget

    
A workflow uses many more tokens than one session. Limit the number of agents in the prompt, or with the size guideline in /config. There is no token limit: watch /workflows and stop the run if it grows too large.

    
Use one when the work splits into many parts that each need a check: a migration, an audit, a research task, the triage of a thousand items.

    
Use a skill instead when the steps are the same each time, such as our process in /make-it-so. A workflow is a plan for one task.

    
Do not use one for a change you can see in one file.

Remote Control: one session

    
Drive a session on this Mac from your phone or a browser. The code, the files and the tools stay on the Mac. Only the chat goes through claude.ai.

    
Run /rc in the session. On a phone with the same account, the session is already in the list of the Claude app: no QR code needed. The terminal and the phone show the same conversation.

    
It needs a claude.ai login in the session. An API key does not work. The Mac must stay awake.

    
All Remote Control traffic goes through Anthropic's servers. At work, check your company's policy first: often it is not allowed. On a personal machine, be careful with what the session can reach.

Keep it safe

    
    
      
  • The Mac only calls out over TLS: no port opens on it
    • 
      
  • Your account is the key: turn on "Require trusted devices", so only your devices can steer a session
    • 
      
  • Permission prompts wait on the phone until you answer: read each one

Remote Control: many sessions

    
Server mode waits for sessions. You start each new one from the phone or from claude.ai/code. It runs on this Mac, in the clone.

    
With --spawn worktree, each session gets its own worktree, as in agent view. Press w in the server to switch to one shared folder.

  

  

    
Start the server in the clone, and leave it running

    
task claude:start -- remote-control --spawn worktree

    


Where the session runs

    

      
Remote ControlOn this Mac. The phone is only a window into it

      
cloud sessionIn the cloud, on a clone from GitHub. The Mac can be off. Start one at claude.ai/code or with claude --cloud

      
--teleportMoves a cloud session into this terminal, with its branch

    

    

    
Keep it safe

    
    
      
  • Start the server in the project folder, not in your home folder
    • 
      
  • Keep the permission prompts on: never start it with `bypassPermissions`
    • 
      
  • Stop the server when you are done: until then it waits for new sessions
    • 
    

  






  

    
The whole picture

    
Each step of the workflow, and the iteration that taught it.

    
The loop found the work. The subagents did it. The skill made it one command. The plugin improved the skill. The workflow found what comes next. Agent view built it in parallel. Remote Control puts it all on your phone.

run the process           /make-it-so      iteration 3
improve the process       a plugin         iteration 4
format each edit          a hook           iteration 4
plan the next work        a workflow       iteration 5

Recap

    
    
      
  • Give Claude a check it can run, then let it run longer.
    • 
      
  • Give each job to the right model.
    • 
      
  • Write your process down once, as a skill.
    • 
      
  • Install what others built before you write your own.
    • 
      
  • Use a workflow when one agent is not enough.
